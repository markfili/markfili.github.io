How arilus.hr is made

A night landscape with a menu perched on its summits, drawn by code on a single canvas. Here is what sits behind it.

The site is a Flutter app compiled to WebAssembly. Nothing on it is laid out in HTML. Every ridge, every letter and every button is painted onto one canvas, the way a game draws its screen. The only image file is the red ring logo; the rest is generated.

1 imagethe logo; the scene is code
2 shadersclouds and film grain, on the GPU
5 ridgesseeded, so they never change
120+ testslayout, content, keyboard, screen readers

The scene, layer by layer

The landscape is painted back to front, like stage scenery. Each layer is a small painter or a shader. The mountains come from fixed random seeds, so the same peaks appear on every visit and at every screen size, which is what lets the menu sit on them.

Two layouts from one skyline

Because the ridges are fixed, the code can find the summits and work out where a bubble fits. On a wide screen each menu bubble perches on its own peak, clear of the logo and the offer line. When the screen is too narrow or too short for that, the bubbles move into a ring around the logo instead, and labels go above or below them so none runs off a small phone.

One set of words, two kinds of reader

A canvas is invisible to search engines and AI assistants: they find no text in it. So the words live in plain files, and the same files feed both the app and a set of plain-text copies.

The canvas itself is readable too. The app turns on Flutter's screen-reader layer from the start, with the wordmark as the page heading and the menu read in order, and every sheet has its own address, such as #/work, so it can be linked to.

The first second

The app takes a moment to download and start. Until it does, index.html shows a plain HTML splash on the same night sky, with a thin glint so a slow connection doesn't look frozen. The handover is staged so the two never overlap.

How it was built

Built with AI coding agents, held to the same routine on every change:

  1. A short written design first, kept in the repository under design/.
  2. Tests for the behaviour, then the code. Layout tests check that no bubble, label or line of text collides at phone, laptop and desktop sizes.
  3. A look at the real thing: the app is built and screenshotted in a browser before a change counts as done.
  4. Content checked against the source repositories, with anything unconfirmed taken out.

To publish, flutter build web --wasm writes the site into docs/, and GitHub Pages serves that folder as arilus.hr.
